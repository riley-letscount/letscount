アニメ『フカシギの数え方』に登場するコンピュータを題材に、格子上の自己回避経路の総数を数えるプログラムです。 通常モードでは深さ優先探索による全探索を行い、高速モード（「おねえさんに教えてあげる」）では frontier 法によって状態を集約しながら数え上げます。 このページの下部からWindows用とMac用のローカル版（GUIアプリ）もダウンロードできます。 参考：shogo82148、原作：『フカシギの数え方』おねえさんといっしょ！みんなで数えてみよう！

通常モード（素朴な全探索） 待機中

n×n のマス目に対して格子点は (n+1)×(n+1) 個。左上がスタート、右下がゴールです。

計数アルゴリズムと並列化の仕組み

本プログラムが数えるのは、n×n のマス目（格子点 (n+1)×(n+1) 個）上で、 左上の始点から右下の終点へ至る、同じ格子点を二度通らない経路（自己回避経路）の総数です。 高速モード（「おねえさんに教えてあげる」）では、経路を1本ずつ列挙するのではなく、 frontier 法（frontier-based dynamic programming）の一種である Simpath アルゴリズムを用い、 部分経路に関する情報を状態として集約しながら数え上げます。Simpath は、ゼロサプレス型二分決定図（ZDD）の 節点共有と等価な合流を、決定図そのものを構築することなく実行する手法です。 以下、状態表現、状態遷移、並列化方法、採用したデータ構造とその実測上の根拠を順に述べます。 シングル／マルチのいずれでも、状態の表し方と遷移規則は共通です。

  • frontier（境界）：格子の辺を行優先順序（上から下、左から右）で1本ずつ処理します。各時点で、処理済みの辺と未処理の辺の双方に接続する格子点の集合を frontier と呼びます。その大きさは最大でも n+1 個程度であり、保持すべき状態はこの frontier 上の情報に限定されます。状態表は辺1本の処理（レイヤ）ごとに次世代へ作り替え、前世代は解放します。
  • 状態表現（mate）：各状態は、frontier 上の各格子点の次数（0、1、または2）と、次数1の格子点（部分経路の端点）同士の対応関係（mate）から構成されます。部分経路同士は交差しないため、この対応は非交差マッチングとなり、括弧列として表すことができます。同一の状態に到達した部分探索は区別せず1つに合流させ、それぞれが表す経路数を合算します。この合流が、経路を個別に列挙する場合との計算量の差を生みます。件数（経路数）の保持方法は、シングルでは BigInt、マルチでは後述する基数1e9の肢表現です。
  • 状態の符号化（2ビットパック）：状態は「単一の数値キーと件数の組」として保持し、遷移はキーに対するビット演算（プラグ符号の抽出、括弧の対応付け、フィールドの書き換え）のみで実行します。キーは、frontier の各セルについてプラグ符号を1セル2ビット（0＝プラグなし、1＝開き括弧、2＝閉じ括弧、3＝X）で表した部分と、次数2のセルを1セル1ビットで示す部分を、1つの整数に詰めたものです。始点に接続する端点プラグと終点に接続する端点プラグは、どちらも同じ記号 X で表します。この統合が異なる状態を混同しないのは、終点側のプラグは終点セル自身の括弧の相手として判別でき、始点側のプラグは常にその左に現れるためです。X と括弧プラグを接続すると端点側が部分経路を吸収して結果も X となり、X 同士の接続は始点側と終点側の接続、すなわち経路の完成に対応します。キーは16×16以下では JavaScript の安全整数（Number）の範囲に収まりますが、17×17以上では収まらないため、符号化と遷移規則はそのままに、キーの型のみを BigInt に切り替えます。
  • 並列化（シャーディングとバリア同期）：マルチモードでは、次レイヤの状態表を、キーのハッシュ値によって Worker 数と同数のシャードへ分割します。各シャードは互いに素であり、その和集合は状態表全体と一致するため、各 Worker が担当するシャードだけを保持・合流しても、状態の重複や欠落は生じません。各 Worker は、生成した（キー, 件数）の組を宛先シャードごとに仕分けし、型付き配列に詰めてメインスレッド経由で転送します（件数は基数1e9の肢に分解して転送します）。メインスレッドはデータの中継と、レイヤごとのバリア同期のみを行い、状態の合流計算は行いません。なお、状態数が4,096未満のレイヤでは転送量に対して計算量が小さいため、単一の Worker で処理し、状態数がこの値以上になった時点でシャードへ分配します。
  • 状態表のデータ構造と件数の表現：マルチの状態表は、連想配列（Map）ではなく、キー順に整列した密な型付き配列で保持します。1状態の内訳は、キー（下位・上位各4バイト）と件数（基数1e9・12肢＝48バイト）の計56バイトです。合流は、生成したレコードをキー順に整列し、線形走査によって同一キーの件数を合算する方式で行います。Map のエントリやオブジェクトを介さないため1状態あたりの容量は小さくなりますが、その代償として、レイヤごとに整列のための計算が必要になります。件数を BigInt ではなく基数1e9の肢（limb）の列として保持するため、合流のたびに BigInt オブジェクトを割り当てる処理も生じません。肢数は12であり、表せる上限は108桁です。これは19×19の経路数（88桁）と20×20の経路数（97桁）を上回るため、全サイズで桁あふれは生じません。シャードの割り当ては静的です（各 Worker が自分のシャードを担当します）。
  • 測定結果と、採用しなかった方式：保持方式の効果を測定した結果の一例では、Map で保持する方式に対して、13×13で9.95秒から8.69秒へ（約13%の短縮）、14×14で39.61秒から29.33秒へ（約26%の短縮）となり、サイズが大きいほど短縮率が広がりました。これは、サイズの増大に伴って状態表の合流にかかる処理の割合が増えることと整合します。一方、処理の空いた Worker が他のシャードの処理を引き受ける動的な割り当てについては、同じ測定で13×13が9.25秒、14×14が29.57秒と、静的な割り当て（8.69秒、29.33秒）に対する改善が見られなかったため、採用していません。ブラウザ版ではシャード間のデータ受け渡しがメインスレッド経由の転送を必要とするため、割り当てを均す効果よりも転送の費用が上回ったものと考えられます。また、件数を複数の剰余で表して複数回計算し、中国式剰余定理（CRT）によって元の値を復元する方法は、メモリ使用量の削減には有効となり得ますが、本ブラウザ版の実装には含めていません。なお、これらの測定値は特定の端末・ブラウザにおける一例であり、絶対値は実行環境によって変動します。
  • メモリ使用量の推定方法と限界：ブラウザの仕様上、Worker が実際に使用しているメモリ量をページから直接取得することはできないため、結果欄の「メモリ目安」は、最大レイヤ幅（同時に保持する状態数の最大値）に1状態あたりの容量を乗じて推定しています。シングル（Map と BigInt による保持）については、実測したライブヒープ（1状態・1レイヤあたり約70バイト）を基礎に、遷移時に前後の2レイヤが同時に存在することと、ガベージコレクション（GC）の余裕を見込んで、約130〜320バイト／状態としています。マルチ（密な保持）については、型付き配列の実容量（1状態56バイト）を基礎に、前後2レイヤと整列用インデックスが同時に存在する分を見込んで、約90〜190バイト／状態としています。推定に用いる最大レイヤ幅は、14×14までは実測値、15×15以上はサイズあたりの伸び率（約2.75〜2.82倍）に基づく外挿値です。したがって、これらの値は幅を持った推定であり、実際の使用量はブラウザ、端末、GC の実行時期によって前後します。
  • 対称性による削減：始点から最初に進める方向は右または下のいずれかであり、格子の転置対称性により、右に進む経路数と下に進む経路数は等しくなります。本実装では最初の1辺を右方向に固定して数え上げ、最後に結果を2倍します。
  • 枝刈り（不要な遷移の除外）：次の条件に該当する遷移は、完成した経路に至ることがないため除外します。終点に到達した経路をさらに延長しないこと、次数が2を超える辺を加えないこと、始点と終点については次数1を超える辺を加えないこと、部分経路の両端を接続して閉路を形成しないこと、frontier から外れる格子点に端点（次数1）が残る場合はその状態を打ち切ることです。これらは必要条件に基づく除外であり、正しい経路を除外することはありません。
  • 実行環境への依存：マルチモードの効果は、利用可能なコア数とブラウザの実装に依存します。コア数の少ない端末や iPhone では、データ転送と合流の費用のため、シングルモードより処理時間が長くなる場合があります。マルチモードは、コア数の多いデスクトップ環境（特に Windows）での利用を想定しています。
  • 表示更新の間引き：描画と進捗表示が計算の妨げにならないよう、通常モードの経路描画は約90ミリ秒ごと、高速モードの進捗報告は250ミリ秒ごとに更新します。大きな経路数は、桁区切りと桁数を併記して表示します。

通常モードは、深さ優先探索によって経路を1本ずつ列挙するため、サイズの増大に伴い計算量が急激に増加し、 大きなサイズでは現実的な時間内に終了しません。高速モードとの比較を通じて、状態の集約が計算量に与える効果を確認できます。 計算結果の正しさは、既知値（OEIS A007764）との照合、および起動時に実行する自己検証によって確認しています。

GUI版（ローカル実行用）

このページと同じ問題を扱う GUI アプリです。ダウンロードしてローカルで実行できます。 最初にシングル／マルチを選びます。シングルはスレッド1固定、マルチはスレッド数の「自動」（端末の実際の論理コア数、上限128）が初期値で、手動選択もできます。 状態の保持と合流はハッシュ表による方式のみを用い、キー順に整列して合流する方式は用いません。マルチ実行時は、状態表を分割した処理単位を、処理の空いたスレッドへ動的に割り当てます。推定メモリ使用量が上限を超える場合は、保持方式はハッシュ表のまま、件数を複数の剰余で表す方式へ自動的に切り替え、中国式剰余定理によって元の件数を復元します。サイズは 1×1〜20×20 対応で、17×17以上ではメモリ大量使用の警告を表示します。 ブラウザの制限を受けず、CPUコアをそのまま使えるのが利点です。Windows用と Mac用があります。
